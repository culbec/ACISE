### 3.2 Phase 9 - sandbox on `culbec/ACISE` (Claude builds; the user approves every push)

Goal (E4): does the frozen pooled model behave as expected on new runs whose cause is known? The sandbox is a repository the model has **never seen**, so E4 is also a transfer test, like E3.

**Pushing branches and opening pull requests on the public `culbec/ACISE` repository is outward-facing.** Claude asks before the first push. The user decides whether Claude pushes or the user runs the generator script.

1. **Dedicated branch and workflow.** The branch `ci-sandbox` (name to confirm with the user) is an orphan branch (`git switch --orphan ci-sandbox`), with no history shared with `main`. It holds only:
   - a small Python package with real tests, written for this experiment (a few modules, enough code for mutations to land in);
   - `.github/workflows/sandbox.yml`, the only workflow on the branch.

   The workflow:
   - triggers: `push` on `ci-sandbox` and `ci-sandbox/**` scenario branches, and `pull_request` into `ci-sandbox`. It lives only on this branch, so `main` never runs it;
   - steps: checkout, `astral-sh/setup-uv`, `uv sync`, `ruff check`, `pytest`, with stable job names, because labels read the job list;
   - no secrets.

   Nothing under `projects/` and nothing on `main` changes. The generator and `validate/sandbox.py` live in `projects/2` on the project branch, as tooling, and only *write* to the sandbox branch.
2. **Registry.** Add `culbec/ACISE` with the new workflow id to `config/targets.json`, `"enabled": false`, so it is never trained on and is not in the pool hash.
3. **Scenario generator,** `scripts/sandbox_scenarios.py`, seeded, with the order recorded:
   - Change shapes: small or large diff; source only or source plus tests; one or many directories; workflow file touched or not.
   - Breakage kinds:
     - none: comments, docstrings, formatting, local renames;
     - code defect: a fuzzed mutation of the sandbox package (flipped comparison, off by one, swapped arguments, dropped branch). It is kept only if a local run of the covering test file fails, so every breakage is a real defect caught by a test;
     - CI break: an invalid step, a failing command or a missing dependency in the workflow file.
   - Every shape appears both broken and unbroken.
   - Warm-up: at least 30 unbroken changes before the first scored run, because history features need earlier runs.
   - At least 40 scored runs; state the breakage rate.
   - Each scenario is one branch `ci-sandbox/<n>-<shape>` cut from `ci-sandbox` and pushed. Part of them also get a pull request into `ci-sandbox`, so both events occur. Unbroken scenarios are merged into `ci-sandbox`, so the history grows as in a real project; broken ones are not.
   - The generator works in a separate worktree of the sandbox branch (`git worktree add`), never in the project checkout.
4. **Prediction before the run ends.** The generator waits for the run to appear, then calls the model and appends one line to `results/sandbox/predictions.jsonl`: the scenario, run id, prediction, p_fail, decision path, imputed features and `predicted_at`.
   - `live.predict_run` refuses a source that is not in the sidecar. Add a separate path for a registry target outside the pool. It builds the row from the sandbox's own collected history with that target's `TargetConfig`, and is marked `in_pool: false`.
   - Put the sandbox code in a new `validate/sandbox.py`: `live.py` is at 487 lines, close to the 500-line limit.
5. **Report** (`sandbox.report(predictions.jsonl)`): add each run's conclusion once it has ended. Show the confusion matrix, MCC, and Parrot and majority on the same runs. Add a per-scenario table, plus the imputed features per prediction. Check that no prediction was made after its run completed.
6. **Workflow analysis.** Collect the sandbox target with the existing collector and run `label-check` on it: event mix, failed-job breakdown, infrastructure share, and whether CI breaks show up as failures or as `startup_failure` with no jobs. That decides whether CI breaks fall under the label at all. State the outcome in the report either way.
7. **Notebook.** New `validation.ipynb` section 5 "Sandbox": scenario matrix, warm-up summary, `sandbox.report` tables, label-check table. Mark the network cells `live` and add a test to `test_notebooks.py` with a stubbed `predictions.jsonl`.
8. **Tests:** `tests/test_sandbox.py` covers the generator (seeded order, every shape both ways, a mutation is kept only if a test fails) and the report (metrics, and refusal of a prediction made after completion).

Expected risk: the sandbox has a short history, so most history features are imputed with the training medians. The prediction then rests mostly on change features. The report says so, using the imputed-feature table.
